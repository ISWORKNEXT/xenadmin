## Findings requiring attention before claiming parity

### HP-N1 — CHIN creation reports acceptance as completion

`Connection::create_chin_network` in `crates/xen-core/src/network.rs:234` submits `Async.Tunnel.create` using `request::<String>` at lines 280–284 and never waits for the returned task through `wait_task_value` or `async_task`. After receiving handles for all members it returns `Ok(())`. A later task failure is therefore not returned to the caller, and cleanup runs only for submission errors. Upstream `CreateChinAction.Run` calls synchronous `Tunnel.create`. This is a high-confidence static finding, not a reproduced host failure. It also means a successful local create notification is insufficient evidence of working tunnels.

### HP-N2 — Host action wrappers omit original operational workflow

`host_action` simply resolves UUID and waits one async RPC. Upstream host reboot/shutdown/evacuation classes include VM handling, HA tolerance, coordinator and recovery behavior. Treat these as partial workflows even though all buttons exist. Do not use the original feature name as evidence that those preconditions and recovery steps are implemented.

### HP-N3 — Pool-wide networking differs materially

Upstream bond creation builds matching bonds across hosts, manages management interfaces and offers LACP hashing. Local creation is single-host, forbids management NICs and fixes LACP hashing to l3. Local SR-IOV creation does not reorder coordinator first. Local VLAN duplicate checks compare device strings across the entire pool. These require multi-host tests and design work, not only a UI rename.

### HP-N4 — DR_task is not disaster recovery

Local `dr.rs` implements DR task creation/deletion. It does not implement metadata replication setup, metadata database sessions, VM recovery, failover/failback/dry run or appliance recovery ordering. The upstream DR commands must remain missing/partial in the matrix.

### HP-N5 — Session-expiry reconnect gap

`workspace.rs::event_loop` marks SESSION_INVALID as a stale live-update failure and exits. `heartbeat_loop` does not include `ApiError::XenCode(SESSION_INVALID, ...)` in the reconnect-producing branches; it falls into `Ok(Err(_)) => failures = 0`. Repeated expired-session responses therefore do not trigger automatic reconnect, although transport failures do. No fault was injected here; this is direct branch analysis. Reconnect also rebuilds inventory without repeating the pool-member production-host policy check in add_connected; old read_only=true remains preserved, but newly-discovered protected membership is not re-evaluated on this path.
